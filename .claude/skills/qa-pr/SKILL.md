# TIMO PR QA 시나리오

대상: $ARGUMENTS (PR 번호. 없으면 현재 브랜치 vs `origin/main`)

AI가 QA를 대체하지 않는다. **"이번 PR에서 사람이 어디를 확인해야 하는지"를 좁혀주는 참고 리포트**를 만든다.

- 파일을 만들거나 코드를 수정하지 않는다. 앱·Playwright도 실행하지 않는다 (1단계)
- 테스트 환경·모킹 기준은 `${CLAUDE_SKILL_DIR}/references/qa-policy.md`를 먼저 읽고 따른다

## Phase 1: 변경분 수집

- PR 번호가 있으면
  - `gh pr view <번호> --json title,body,headRefName,baseRefName`
  - `gh pr diff <번호> --name-only` → 변경 파일 목록
  - `gh pr diff <번호>` → diff 내용
- PR 번호가 없으면
  - `git diff --name-only origin/main...HEAD`
  - `git diff origin/main...HEAD`
- **PR 번호로 실행할 때 로컬 체크아웃은 PR 코드가 아닐 수 있다.** 변경 내용의 기준은 diff다. 로컬 파일은 diff 주변 맥락을 볼 때만 쓰고, 그렇게 추정한 부분은 리포트에 "추정"으로 표시한다

## Phase 2: 변경 파일 분류

`docs/product/*.md` 각 문서 상단 frontmatter의 `sources`(glob)를 읽고 변경 파일마다 아래 중 하나 이상으로 분류한다.

| 분류 | 기준 |
|---|---|
| **스펙 매칭** | 어떤 스펙 문서의 `sources` glob에 걸린다 (여러 문서에 걸리면 모두) |
| **전역 영향** | `src/components/ui/**`, `src/hooks/**`, `src/lib/**`, `src/styles/**`, `src/types/**`, `app/layout.tsx`, `app/providers.tsx`, `app/global-error.tsx`, `next.config.ts`, `package.json` |
| **QA 대상 아님** | `docs/**`, `.claude/**`, `.github/**`, `e2e/**`, `*.stories.tsx`, `public/**` (이미지·아이콘만 바뀐 경우) |
| **스펙 없음** | 위 어디에도 해당하지 않는 런타임 코드 |

- glob 규칙: `**`는 하위 경로 전체, `*`는 한 경로 조각 안의 임의 문자, `(home)`·`[groupId]` 같은 괄호는 글자 그대로
- 스펙 매칭과 전역 영향에 동시에 걸릴 수 있다 (예: `src/lib/api/instance.ts`)
- 변경 파일이 전부 "QA 대상 아님"이면 그 사실만 짧게 알리고 끝낸다

## Phase 3: 스펙 대조

매칭된 스펙 문서를 읽고 diff와 대조한다.

- **스펙 갱신 필요:** 사용자에게 보이는 동작(흐름·문구·예외 처리)이 바뀌었는데 해당 스펙 문서가 이 PR에서 갱신되지 않았다
- **스펙과 다른 변경:** 스펙의 규칙·예외와 다르게 동작하도록 바뀌었다. 의도인지는 판단하지 않고 사람에게 넘긴다
- **스펙 없음:** 매칭 문서가 없는 기능 변경
- **해소된 확인 필요:** 스펙의 `[확인 필요]`·버그 의심 항목이 이 PR로 구현·수정된 것으로 보인다
- PR diff에 스펙 문서 변경이 포함돼 있으면 **변경된 스펙을 기준**으로 대조한다
- 스펙에 없는 세부 구현(타입 이동, 공백 변경 등)은 대조 대상이 아니다

## Phase 4: QA 시나리오 작성 (기본 3개, 최대 5개)

우선순위: ① 이번에 바뀐 동작 → ② 바뀐 코드 근처의 예외 → ③ 같은 화면에서 깨지기 쉬운 기존 규칙(회귀)

- 4개 이상은 "스펙과 다른 변경"이 여러 개라 따로 확인해야 할 때만 쓴다
- 비슷한 확인은 한 시나리오로 묶는다

각 시나리오는 아래를 채운다. **지금 읽는 사람은 리뷰어다.** 테스트 코드 수준의 세부(모킹할 엔드포인트, localStorage 키, 셀렉터)는 쓰지 않는다

- **전제:** 한 줄 (예: "로그인, 친구 캘린더 API 모킹"). qa-policy의 방해 조건은 해당될 때만 짧게
- **단계:** 한 줄, 화살표로 잇는다
- **기대 결과:** 최대 3개. 문구는 스펙·코드에 있는 그대로
- **근거:** 스펙 섹션 또는 `파일:라인` 하나

### 쓰지 않는 것

- **스펙의 "버그 의심"·`[확인 필요]` 항목을 기대 결과로 쓰지 않는다.** 사람 확인 체크리스트로 보낸다
- 스펙에도 diff에도 없는 기대 결과를 지어내지 않는다. 기대 결과를 모르면 시나리오 대신 체크리스트에 "기대 동작 확인 필요"로 적는다
- 자동으로 확인할 수 없는 것(아래 qa-policy의 "AI가 확인 못 하는 것")은 시나리오가 아니라 체크리스트로 보낸다

## Phase 5: 리포트

**분량 목표: 화면 한 장(60줄 안팎).** PR이 커도 늘리지 않고 중요한 것만 남긴다. 아래 형식에 없는 섹션은 추가하지 않는다.

### 섹션별 규칙

- **영향 범위:** 파일 단위가 아니라 **스펙 문서·분류 단위로 한 줄씩.** 파일 수와 무엇이 바뀌었는지만 적는다. "QA 대상 아님"은 개수만
- **스펙 대조:** 항목당 한 줄. 근거 파일 하나
- **사람 확인 체크리스트:** **최대 5개.** "사람만 판단할 수 있고 영향이 큰 것" 순으로 고른다
  - 우선순위: 스펙과 다른 변경의 의도 확인 → PR 본문과 코드가 다른 부분 → 전역 영향 회귀 → 백엔드·실기기 확인
  - 나머지는 마지막 줄에 `기타 N건: 키워드, 키워드` 한 줄로 줄인다

```text
# QA 리포트: <PR 제목 또는 브랜치>

## 영향 범위
- <스펙 문서> — N개 (<바뀐 화면·기능>)        예: groups.md — 11개 (친구 회고, 랭킹, 댓글 시트)
- 전역 영향 — N개 (<공용 모듈>)               예: 전역 영향 — 9개 (ui/Calendar·Modal, 공용 훅)
- 스펙 없음 — N개 (<파일 또는 기능>)          (해당 있을 때만)
- QA 대상 아님 — N개

## 스펙 대조
| 구분 | 스펙 문서 | 내용 (근거) |
(해당 없으면 "스펙과 충돌하거나 갱신이 필요한 변경 없음")

## QA 시나리오
### 1. <제목>
- 전제:
- 단계:
- 기대 결과:
- 근거:

## 사람 확인 체크리스트
- [ ] ...
- 기타 N건: ...

> 스펙은 현재 코드 동작 기준 초안(draft)이라 이미 있는 버그를 정상으로 볼 수 있다.
```

- PR 번호로 실행해서 로컬 코드로 추정한 부분이 있으면 해당 항목 끝에 `(추정)`만 붙인다
