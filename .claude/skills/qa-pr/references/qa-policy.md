# QA 정책

`/qa-pr`이 시나리오의 **전제·모킹·확인 범위**를 정할 때 따르는 기준. 기능 동작 자체는 `docs/product/`가 기준이다.

## 검증 원칙

- 스펙(`docs/product/*.md`)은 현재 코드 동작을 기준으로 쓴 초안(draft)이다
- 스펙의 **"확인 필요 — 버그 의심"** 섹션과 `[확인 필요]` 표시 항목은 **검증하지 않는다.** 사람 확인 체크리스트로만 보낸다
- 결과는 머지 게이트가 아니라 참고 리포트다

## 실행 환경 (현재 기준)

- 로컬·CI의 `pnpm dev` 서버 대상 (`http://localhost:3000`)
  - dev에서는 브라우저의 API 요청이 `/api/proxy/*`를 거쳐 백엔드로 간다
  - Vercel Preview는 로그인 쿠키 문제로 아직 대상이 아니다
- 뷰포트는 모바일 기준. 레이아웃 최대 폭이 440px이다

## 로그인

- `/test-auth`에서 공용 테스트 계정 `test@test.com`으로 로그인한다 (기존 `e2e/`와 같은 방식)
- 비로그인 시나리오는 쿠키 없이 시작한다

## 모킹

- **실제 데이터를 바꾸는 요청(작성·수정·삭제·참여·장착 등)은 모킹한다.** 공용 계정이라 실제로 바꾸면 다른 테스트와 팀원에게 영향이 간다
  - 모킹 패턴: `page.route('**/api/proxy/<엔드포인트>', …)` (dev 전용)
  - 예: 회고는 하루 1개라 실제로 한 번 제출하면 그날 다른 회고 작성 테스트가 모두 409로 실패한다
- 조회 요청(GET)은 실제 백엔드를 써도 된다. 특정 상태(빈 목록, 에러, 특정 값)가 필요하면 모킹한다
- **서버 컴포넌트 요청은 모킹할 수 없다.** 전제에 "실제 계정 상태에 의존"으로 적는다
  - 홈의 사용자 정보(`/users/me`), 온보딩 소개 prefetch
- 에러 시나리오는 해당 API를 4xx/5xx로 모킹해서 만든다

## 시나리오를 방해하는 조건

전제에 필요한 대응을 적는다.

- **서비스 피드백 모달:** 연속 기록일수가 1일이면 홈에 뜬다 → 닫거나, `localStorage`에 `service_feedback_dismissed`를 미리 넣는다
- **앱 설치 안내:** iOS UA이고 홈 화면 앱이 아니면 모든 화면에 뜬다 → iOS UA를 쓰지 않거나 `localStorage`에 `installPromptSeen`을 미리 넣는다
- **길게 누르기:** 그룹 관리 메뉴는 길게 눌러야 열린다 (기존 `e2e/group-manage.spec.ts` 참고)
- **날짜 의존:** "오늘"·연속 기록·캘린더는 실행 날짜에 따라 결과가 달라진다 → 기준 날짜를 고정하거나 응답을 모킹한다

## AI가 확인 못 하는 것 (체크리스트로 보냄)

- 소셜 로그인(카카오·네이버·구글) 실제 흐름
- 푸시 알림 수신, 브라우저 알림 권한 팝업, FCM 토큰 발급
- 기기 공유(`navigator.share`), 클립보드 복사 실제 동작
- 실제 AI 피드백 생성 결과·소요 시간
- 홈 화면 앱(PWA) 설치·실행, 실기기 터치 제스처
- 백엔드 규칙 (해금 조건, 시간대, 권한 검사 등)
- 시각적 품질 (디자인 일치, 애니메이션)
